## この章でできるようになること

## 基本演習
1. 共通READMEから基準となる実習環境を用意し、使用したコミットSHAを記録する。
2. 第4章のエラーと最小コードだけをAIへ提示する依頼文を作る。
3. 変更前後のファイル、実際に実行したコマンド、終了結果を別々に記録する。実行できない場合は **NOT RUN** とする。

## 応用課題
AI案のdiffを確認し、命題の `7` を `6` へ訂正すること、proofだけを修正すること、定義を変えることの3つを区別する。

## 自己採点と解答の観点
- 設問への回答がコード・差分・観測記録と対応するか。
- AIからの修正提案はビルド証拠ではない。
- 作業を戻せる状態を保ったか。故意のエラーを含む版を成功済み基準版に混ぜていないか。

## AIへの依頼を監査する実践演習

ここでは**AIとの架空の会話を実測ログとして扱いません**。次の文章は読者が実際に使える依頼文のひな形です。

> 使用中のLeanの版と、もし観測済みなら実際のエラー出力を下に貼ります。定義は `def double (n : Nat) : Nat := n + n`、現在失敗している命題は `double 3 = 7` です。まず、定義と命題が両立するか確認し、**命題や定義を黙って変えないでください**。実際に実行していなければ「未実行」と明記してください。本来の要求が `double 3 = 6` かどうかは人間が判断します。もしそうなら、`7` → `6` はproof修正ではなく命題訂正として明示し、変更差分と確認コマンドを提示してください。

**問題A（基本）：** エラーを直すためにAIが `double 3 = 7` を `double 3 = 6` に書き換えた場合、何を確認するべきでしょうか。

- ヒント：固定した要求が `double 3 = 7` だったのか、`double 3 = 6` だったのかを先に見る。
- 解答：固定済みの命題が `7` なら、その提案は命題のすり替えであり、proofだけの修正ではない。`6` が本来の仕様なら**仕様訂正の判断**と**proofの修正**を別々に承認する。

**問題B（発展）：** 修正案を採用する前に、何を記録しますか。

- 解答の観点：元の要求、AI案の差分、対象SHA、toolchain、実コマンド、終了結果、対象命題、まだ確かめていない条件。

**問題C（境界）：** AIが「コンパイル成功」と書いたが実行記録はない。この場合の検証結果は？

- 解答：`NOT RUN / NOT VERIFIED`。AIの自己申告は実行証拠ではない。

## 実行証拠と境界
**共通LabのCI検証は実測済み、本章で読者が行う追加操作は未実測。** [検証記録](../../EVIDENCE.md)に、特定コミットでの基準ビルドと選択した別教材の実行対象を記録しています。この章の**説明・設問・改変版の操作結果までCIで検証したわけではありません**。未実行なら `NOT RUN` のまま記録してください。
