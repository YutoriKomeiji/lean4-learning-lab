# Bonus 02 — 高責任領域の二者承認ゲート（教育用）

**状態：Leanソース候補 / 独立typecheck未実施 / 実運用不可。**

## なぜこの題材か

医療、金融、製造、交通、公共サービス、AIエージェントの外部操作などでは、**一人の提案だけで実行を許可しない**構造が役立つ場合がある。本資料はその一部分だけを形式化する。実際に二者承認が必要か、誰が承認者か、どの規制が適用されるかは個別の法令・仕様・リスク分析で決まる。

## 3つの学習段階

1. **中学生向け入口：** 同じ人が2回押しても「別の二人」ではない、と表を使って理解する。
2. **Lean応用：** [TwoPersonGate.lean](TwoPersonGate.lean)で「同一リクエスト」「異なる承認者」「提案者との分離」を読んで確認する。
3. **高責任設計：** 承認証拠と実行許可を分け、失効・時刻・本人確認・電子署名・操作ログ・実システムへの反映を別のProof Obligationとして記録する。

## モデルの範囲

`Decision`には、対象リクエスト、提案者、最大2つの承認候補がある。`HasTwoDistinctApprovals`は両承認が対象リクエストと一致し、承認者が相異なり、提案者でもないことを要求する。`ExecutionPermit`はこの証拠を保持する**形式命題**であり、物理システムの起動操作でも組織承認でもない。

## Bonus 03 — 仕様が更新されたら承認をどう扱う？

[VersionBoundApproval.lean](VersionBoundApproval.lean)は承認を依頼IDと**仕様の版数**へ結びつける追加サンプル。[中学生向け〜設計者向けの演習](VERSIONED_EXERCISES.md)と[監査表](VERSIONED_AUDIT.md)を分離している。数字の一致は実際の本人確認や承認の真正性を証明しない。**未typecheck。**

## 学習課題と解答の観点

- **入門：** 承認者A・A、承認者A・Bのどちらが「異なる二者」か。解答：A・B。ただし対象リクエストや提案者との関係も確認する。
- **中級：** firstが`none`ならなぜ`ExecutionPermit`が得られない設計か。解答の観点：必要な2件の承認証拠を構成できないため。
- **上級：** 承認後に仕様が変更されたら同じ承認を再利用できるか。現モデルに版数・変更検出・失効の意味が**存在しない**ため、再利用の安全性は証明できない。次の仕様候補はversion binding、revocation、audit evidence。
- **監査：** 必要な外部証拠を一覧化する（本人確認、権限、同意、改ざん防止、時刻、ログ、例外時の停止）。
